# 安装证据与管理边界

[English](INSTALLATION-EVIDENCE.md) | 简体中文

本次增量新增只读观察结果，不创建安装凭证，不证明最初由谁安装程序，也不授予移除或
升级软件包的权限。注册表中的安装配方与当前机器上观察到的事实保持分离。

## 报告内容

`inspect_installation` 返回已有安装探测结果，以及候选实例、歧义标记和可选说明。
每个实例分别呈现以下信息：

- `path`：通过应用的命令搜索找到的绝对候选路径。
- `resolvedPath`：发现文件的规范化真实路径。Windows 批处理启动器仍解析为批处理文件本身，不会自动解析为它启动的程序。
- `entrypointPath`：实际的包入口；仅在受支持的链接或启动器映射已验证时提供。
- `version`：针对唯一选定的活动实例，通过有界命令执行解析出的版本。注册表和包 manifest 中的版本字符串不能替代实测结果。
- `source`：关联未知的原因，或观察到的 npm 包、包根目录、全局 root、prefix 和确切的包管理器入口。

该列表是 PATH 观察结果，不是完整的整机盘点。指向同一目标的重复别名不算不同安装。
其他候选项会被展示，但不会执行其版本命令。目标不同、检查失败或观察结果不一致时，
不能静默选定写入目标。

自定义注册表 shell 验证可以保留原有的有界状态结果，但不会据此推断实例路径、实测
版本或 npm 归属。不会为了方便获得结果，将不受支持的 Windows 启动器插入 shell
命令中执行。

## npm 关联

受支持的适配器使用固定的包标识和命令名。安装配方匹配、包管理器报告包名，或目录名为
`node_modules`，都不足以建立关联。关联需要下列证据链保持一致：

1. 解析一个确切且受支持的 npm 管理器及其实际调用方式。
2. 查询它的全局 prefix 和 root，并验证其规范化后的目录布局。
3. 在大小限制内读取包 manifest，确认包名和 bin 映射与预期完全一致。
4. 拒绝链接包和逃逸出包目录的入口。
5. 通过规范化链接目标或完整受支持的 Windows 启动器模板，将选定的可执行文件绑定到该确切 bin。

Windows npm 的 prefix 重定向必须遵循启动器语义，不能假定启动器一定选择相邻的
npm CLI。未知模板、额外的启动器命令、不一致的 root 或冲突证据，都会保留为未知。
不能仅因无法建立 npm 关联，就抹去成功获得的安全版本探测结果。

UI 将成功结果显示为“npm 全局目录匹配，安装历史未知”。它不会声称历史上由 npm 或
AgentDeck 安装了该软件。这是避免意外误认的一致性检查，不是对发布者身份的密码学
验证，也不是用于防御其他同用户权限进程的沙箱。

## 执行与写入边界

已知实例的探测使用明确的程序和分离的参数。输出大小、输入文件大小和运行时间均有
限制；原始 stderr 不会作为证据返回。AgentDeck 不会将凭据或 npm 配置内容解析或
返回为来源证据，但 npm 本身可能读取自己的配置。测试使用临时目录、合成启动器和
注入的包管理器结果。

“只读”描述的是 AgentDeck 请求的操作：检查期间不安装、升级、卸载，也不写入 Agent
配置。不过，它确实会执行本地版本查询和 npm 查询程序。这些程序可能读取自己的配置、
更新缓存或日志，或产生其他副作用；探测器不是操作系统安全沙箱。限制分别作用于每个
子进程和被检查的输入/输出，并不保证每次文件系统操作或整个刷新流程都在某个总时限
内完成。

软件安装与配置保持分离，只有获得可靠的 `not_detected` 结果后才会继续安装。配置操作
在准备 profile 或备份前，会检查受支持的适配器和最新的实例歧义情况；核心在应用配置
前还会再次检查。过期的前端数据不能用于执行操作。

自动卸载在所有层面仍然关闭，即使 npm 目录已匹配也不例外。未来通过同一来源管理软件，
需要单独确认实例，并由后端计划在操作前重新验证其管理器、prefix、包、启动器和入口。
观察结果 DTO 不是这样的执行计划。本次未实现升级支持、持久化安装凭证，或对所有并发
外部改动的防护。

来源适配器边界未来可以扩展到原生 Agent 或 DSH 插件，不会假定每个 Agent 都是 npm
包。原生插件能力协商、配置对账和包生命周期管理仍是独立的设计工作，不能从当前注册表
推断出这些能力字段。
