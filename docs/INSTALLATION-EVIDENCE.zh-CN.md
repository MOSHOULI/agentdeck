# 安装证据与管理边界

[English](INSTALLATION-EVIDENCE.md) | 简体中文

当前开发分支提供只读安装观察，以及独立、范围受限的 npm 纯安装适配器。两者都不创建
持久化安装凭证，不证明最初由谁安装程序，也不授予移除或升级软件包的权限。注册表中的
安装配方与当前机器上观察到的事实保持分离。

这些改动计划随 v1.2.0 交付，不在已发布的 v1.1.1 安装包中。是否已发布以对应 Release
为准，请核对其中的 `BUILD_COMMIT.txt` 与源码修订版本，参见 [README](../README.md)。
版本字符串相同不能证明包含相同代码。

## 报告内容

`inspect_installation` 返回已有安装探测结果，以及候选实例、歧义标记和可选说明。
每个实例分别呈现以下信息：

- `path`：通过应用的命令搜索找到的绝对候选路径。
- `resolvedPath`：发现文件的规范化真实路径。Windows 批处理启动器仍解析为批处理文件本身，不会自动解析为它启动的程序。
- `entrypointPath`：实际的包入口；仅在受支持的链接或启动器映射已验证时提供。
- `version`：针对唯一选定的活动实例，通过有界命令执行解析出的版本。注册表和包 manifest 中的版本字符串不能替代实测结果。
- `source`：关联未知的原因，或观察到的 npm 包、包根目录、全局 root、prefix 和确切的包管理器入口。

该列表是 PATH 观察结果，不是完整的整机盘点。指向同一目标的重复别名不算不同安装。
其他候选项会被展示，但不会执行其版本命令。目标不同、检查失败或观察结果不一致时，
不能静默选定写入目标。

自定义注册表 shell 验证可以保留原有的有界状态结果，但不会据此推断实例路径、实测
版本或 npm 归属。不会为了方便获得结果，将不受支持的 Windows 启动器插入 shell
命令中执行。

## npm 关联

受支持的适配器使用固定的包标识和命令名。安装配方匹配、包管理器报告包名，或目录名为
`node_modules`，都不足以建立关联。关联需要下列证据链保持一致：

1. 解析一个确切且受支持的 npm 管理器及其实际调用方式。
2. 查询它的全局 prefix 和 root，并验证其规范化后的目录布局。
3. 在大小限制内读取包 manifest，确认包名和 bin 映射与预期完全一致。
4. 拒绝链接包和逃逸出包目录的入口。
5. 通过规范化链接目标或完整受支持的 Windows 启动器模板，将选定的可执行文件绑定到该确切 bin。

Windows npm 的 prefix 重定向必须遵循启动器语义，不能假定启动器一定选择相邻的
npm CLI。未知模板、额外的启动器命令、不一致的 root 或冲突证据，都会保留为未知。
不能仅因无法建立 npm 关联，就抹去成功获得的安全版本探测结果。

UI 将成功结果显示为“npm 全局目录匹配，安装历史未知”。它不会声称历史上由 npm 或
AgentDeck 安装了该软件。这是避免意外误认的一致性检查，不是对发布者身份的密码学
验证，也不是用于防御其他同用户权限进程的沙箱。

## 执行与写入边界

已知实例的探测使用明确的程序和分离的参数。输出大小、输入文件大小和运行时间均有
限制；原始 stderr 不会作为证据返回。AgentDeck 不会将凭据或 npm 配置内容解析或
返回为来源证据，但 npm 本身可能读取自己的配置。测试使用临时目录、合成启动器和
注入的包管理器结果。

“只读”描述的是 AgentDeck 请求的操作：检查期间不安装、升级、卸载，也不写入 Agent
配置。不过，它确实会执行本地版本查询和 npm 查询程序。这些程序可能读取自己的配置、
更新缓存或日志，或产生其他副作用；探测器不是操作系统安全沙箱。限制分别作用于每个
子进程和被检查的输入/输出，并不保证每次文件系统操作或整个刷新流程都在某个总时限
内完成。

## 纯软件安装

安装软件与应用配置是两个独立操作。安装必须有受支持的固定 npm 适配器，不能只凭注册表
shell 命令或 PATH 的 `not_detected` 结果执行。当前允许的映射将 Codex、Claude Code、
OpenCode、Gemini CLI 和 Pi 分别绑定到确切的包名和验证命令；注册表中的安装方式与配方
也必须匹配适配器。`opencode-ai` 是文档明确列出的 OpenCode V1 途径，不表示支持 V2。
此安装路径不会执行手动条目或任意 shell 配方。各 Agent 的边界及上游
要求见 [注册表来源核验](REGISTRY-SOURCES.zh-CN.md)；列入目录不等于本机可用该适配器。

执行安装器前，后端会：

1. 要求完整的可执行文件搜索，且不存在已有候选。已有、不可检查或存在歧义的候选都会阻止安装。
2. 解析受支持的 npm 入口及确切的 Node 可执行文件，核对 npm 的包/bin 映射并记录文件摘要。未知管理器 wrapper 会被拒绝。
3. 查询该管理器的全局 prefix 和 root，验证受支持的布局，并要求 prefix 已存在且可检查。目标目录不能通过链接或不可用的路径分量重定向。
4. 确认包和启动器目标不存在，**包括不在 PATH 中的已有包或启动器**。无法读取不能视为不存在。Windows 检查覆盖 npm 启动器及同名可执行文件冲突，而不只检查当前 PATHEXT 结果。
5. 紧邻执行前重新生成计划；证据变化时拒绝继续。

命令使用分离参数、已检查的管理器和显式 `--prefix`，不会经 shell 执行注册表命令，也
不会另建一个不同的安装 prefix。命令关闭 force、audit、fund 和 progress 选项。
Pi 另加 `--ignore-scripts`，但并非所有 Agent 都关闭生命周期脚本。安装子进程有五分钟
运行时间限制，捕获的输出也有大小限制。同一进程内只允许一个安装任务；这不是针对其他
程序的锁、发布者签名验证或 npm/包生命周期脚本沙箱。npm 可以下载依赖并写入自己的文件。

npm 结束后，后端重新检查管理器，并要求唯一的活动实例具有实测版本，且入口、包、全局
root、prefix 和管理器与计划一致。仅 npm 成功退出不足以宣告安装成功。如果安装器失败、
超时，或执行完成但后置核验失败，**软件可能已安装或发生部分改动**。AgentDeck 会报告
不确定性，**不会自动回滚或卸载**。重试前先刷新和检查；已有包会阻止新安装，不会静默变成
升级操作。

安装不初始化 profile、密钥库或 Git 备份，也不应用配置。桌面操作需要确认，CLI 需要
`--yes`。临时执行计划由后端重新生成，不会把 UI 传入的计划当作可重复使用的授权，也不会
将它保留为历史归属证明。

## 配置与同步

“应用配置”和 `deploy --action configure --yes` 不执行安装器。在准备 profile 或备份前，
必须已有受支持的 profile 适配器、最新且成功的安装验证，并且没有实例歧义；核心在应用
配置前再次检查。缺失、失败、不支持或有歧义的安装观察不能授权配置。唯一且已验证的实例
仍可能没有已知的包关联；仅这一点不会禁用受支持的配置适配器，也不能证明安装来源。

个性化同步在准备 profile 前及写入前使用相同规则。CLI `sync` 在创建备份或写入任何目标
前，先检查所有已选个性化目标。仅导出记忆不新增安装前提。MCP 独立的离线配置语义保持不变。
过期前端状态不能绕过后端检查。目录中已关闭的适配器保持关闭；来源匹配或安装成功都不会
自动开放这些适配器。

## 尚未开放的管理与验证边界

自动卸载和软件升级仍未开放，即使 npm 目录已匹配、CLI 已传入 `--yes` 也不例外。请使用
原安装方式处理这些操作。未来通过同一来源管理软件，需要另外审查执行计划；观察结果 DTO
和纯安装计划都不授予这种权限。本次未实现持久化安装凭证，或对所有并发外部改动的防护。

安装/来源及配置守卫测试使用隔离的临时 HOME、合成包与启动器、注入的进程结果或安装器回调。
它们不安装真实 Agent，不验证真实登录或服务商，也不证明 Windows 桌面 GUI 完整流程已通过。
不要运行已忽略的真实环境测试来验证本次增量。平台专属检查仍需要对应原生平台；Linux 测试
通过不代表已执行 Windows 检查。

来源适配器边界未来可以扩展到原生 Agent 或 DSH 插件，不会假定每个 Agent 都是 npm
包。原生插件能力协商、配置对账和包生命周期管理仍是独立的设计工作，不能从当前注册表
推断出这些能力字段。
